## 1. Read this first

DOMHamster is a WebMCP-native, human-approved volunteer coordination application. A browser agent can read privacy-minimized operational data, create and repair an assignment draft, prepare an exact version for human review, commit only after a human approves that version, and access selected fictional contacts only after commit. The human retains exclusive control of assignment locks, approval, rejection, cancellation, discard, and reset.

The product direction, domain model, tool contracts, architecture, UI, security model, testing plan, release process, and submission plan were frozen in the approved waterfall master plan. Do not redesign the product unless a verified defect or hackathon compliance issue requires a narrowly scoped correction.

The immediate job is **verification and release completion**, not new feature development.

## 4. Product contract

### 4.1 One-sentence definition

DOMHamster is a WebMCP-native coordination board where an AI agent drafts and repairs volunteer assignments while a human coordinator visibly edits, locks, and approves consequential decisions.

### 4.2 Canonical scenario

| Item | Frozen value |
|---|---|
| Scenario | Fictional non-emergency community assistance in Riyadh |
| Requests | 8, `R-101` through `R-108` |
| Volunteers | 5, `V-01` through `V-05` |
| Time zone | `Asia/Riyadh` |
| Maximum workload | 3 assignments per volunteer at the product-policy level |
| Special constraint | `R-104` requires Arabic support |
| Privacy boundary | Contact details are separate and unavailable before commit |
| Reset | Deterministic return to the canonical fixture |

### 4.3 Canonical demonstration journey

1. Open or reset to `READY`.
2. Agent reads privacy-minimized requests and volunteers.
3. Agent creates a complete valid draft.
4. Human changes `R-105` from `V-01` to `V-03` at `13:00`.
5. Human locks `R-105`; the app enters `DRAFT_INVALID` because it overlaps `R-106`.
6. Agent validates and repairs only `R-106`, moving it to `V-05` at `13:00`.
7. Locked `R-105` remains unchanged and the app returns to `DRAFT_VALID`.
8. Agent prepares the exact draft version for approval.
9. Human reviews and approves that exact version.
10. `commit_assignment_plan` appears for the approved version and expires after 120 seconds.
11. Agent commits once; replay is rejected and the app enters `COMMITTED`.
12. Agent may request selected fictional contacts and recent audit history; contact access is request-scoped and audited.

## 6. Architecture

| Layer | Current implementation |
|---|---|
| Front end | React 19, TypeScript 6, Vite 8 |
| Domain | Pure TypeScript fixture, validation, commands, state machine, approval, commit, audit |
| Store | Serialized FIFO dispatch with transaction-safe persistence |
| Persistence | Versioned `localStorage` envelope with corruption and reload recovery |
| Agent interface | Twelve strict WebMCP contracts with closed JSON Schemas and Ajv validation |
| Runtime | Capability detection, state-aware registration, abort-based cleanup, observed-registration diagnostics |
| UI | Judge-facing workspace, requests, volunteers, assignment editor, locks, validation, approval, committed summary, drawers, reset, responsive/accessibility hardening |
| Hosting plan | Netlify static deployment with source-controlled headers |
| Backend | None |
| Runtime secrets | None |
| External runtime APIs | None |

Important rule: handlers call the shared application store and domain commands. They do not scrape, click, or infer state from presentation DOM.

## 10. Exact release command

Prerequisites:

- clean checkout of candidate commit;
- Node 24 and npm 11.17;
- successful `npm ci`;
- installed Playwright Chromium;
- authentic 50-trial evaluation JSON.

Run:

```bash
npm run verify:release -- --eval-results /absolute/path/to/authentic-50-trials.json
```

The runner executes, in order:

1. `npm run verify`
2. `npm run test:e2e`
3. `npm run verify:bundle`
4. `npm run verify:licenses`
5. `npm audit --audit-level=high`
6. `npm run eval -- --results <file>`
7. `npm run release:manifest`
8. `npm run release:verify`

It must stop on the first failure. Fix each failure with a focused RED–GREEN cycle and rerun the complete sequence on the new exact head.
